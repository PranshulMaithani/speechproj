WHY THIS FILE EXISTS

Your prior sweep showed a 19-point F1 collapse from 20% test (0.81) to audios6
test (0.61). The cross-tabs confirmed this is client-shift: audios2/4/5 are
client A and audios6 is client B. Two interventions target it directly:

  (1) per-client feature standardization   -- removes first-order client drift
  (2) few-shot client adaptation           -- the realistic deployment workflow

Plus two cheap-but-important hygiene fixes the cross-tabs revealed:

  (3) drop ALLSTAR             -- it costs 2-3 F1pt on both test sets
  (4) keep text_features=true  -- helps a6 specifically by ~0.8pt
  (5) add 'linear' architecture -- sanity baseline (logistic regression)

The new CLI flags live on both ec2/neural_baseline_train.py and
ec2/xgboost_train.py:

    --per_client_standardize  true | false   (default false)
    --fewshot_frac            FLOAT          (default 0.0 = disabled)

Placeholders (same as COMMANDS.txt):
    <UPLOAD>   = the upload/ folder on EC2 (e.g. /opt/data/upload)
    <RUNS>     = where training outputs land (e.g. /opt/runs)

Every recipe below is independent. Run them in order so the cross-comparison
through analyze_collated_results.py keeps making sense.

import glob, os, pandas as pd
frames = []
for f in sorted(glob.glob('<RUNS>/*/summary*.csv')):

    df   = pd.read_csv(f)
    df['run']     = run

    df['recipe']  = run.split('_')[0]

combined = pd.concat(frames, ignore_index=True)

--------------------------------------------------------------------------------
WHAT TO LOOK AT IN report_v2.txt
--------------------------------------------------------------------------------

1. QUICK TAKEAWAYS section. The "axis impact" table now has 'recipe' as one
   of the axes -- that's the recipe-level F1 swing. If recipe r1 (per-client
   std alone) moves the mean F1 by more than 3pt, the diagnosis is right.

2. The 2-axis cross-tab head x recipe. Tells us whether per-client std and
   few-shot help NN and XGB equally, or whether one head benefits more.

3. BEST per (head x recipe) section -- shows the best single variant per
   condition. This is the "what would I deploy" number per recipe.

4. The recall@p85, recall@p90 columns: AUC was already 0.92 on a6, the
   problem was threshold-tuned F1. After per-client std, recall@high-precision
   should go up substantially (the ranking was good; calibration was off).

--------------------------------------------------------------------------------
NOTES
--------------------------------------------------------------------------------

* --per_client_standardize uses FEATURES only -- no labels touched. This is
  a legitimate unsupervised step. It centers each client's WavLM/Whisper
  (and feat_*) on its own mean/std, computed from ALL of that client's rows
  (train + test). Removes first-order client drift.

* --fewshot_frac uses LABELS from the carved candidates. That's the deal:
  to adapt to a new client you label some of their candidates. Fewshot
  candidates are candidate-disjoint with test candidates (verified by
  assert_no_group_leak).

* If a recipe takes too long because of n_augs=8: drop --use_augs all and
  re-run. Augs added 1pt on average; they're not where the wins are.

* The 'linear' arch is now in ARCH_CONFIG. If linear matches tiny on a6,
  drop default (it's overfitting client artifacts). If linear LOSES to
  tiny, keep tiny.

* The ALLSTAR rows still exist in gt.csv -- nothing was deleted. They
  just aren't in --train_only_batches anymore. To force-include them
  later (e.g. for an explicit ablation showing they hurt), add back
  --train_only_batches 2676,2677.
